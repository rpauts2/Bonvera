# Cashback Bot — реферальный сервис и контроль выплат

Русскоязычный Telegram-бот для каталога партнёрских предложений, проверки доказательств, начисления кэшбэка, реферальных операций и ручных выплат через СБП.

| Категория | Количество |

| Букмекеры | 6 |
| Выдача займа (МФО) | 52 |
| Заявки МФО (CPL, займ не нужен) | 19 |

Суммы «Я плачу», целевые действия и холды перенесены из пользовательского списка. Это именно предполагаемое вознаграждение пользователю, а не доход партнёрской сети. Комиссия сети по каталогу не задана и равна 0 до получения подтверждения из postback или ручной сверки. Не следует считать её прибылью.

В исходных данных есть партнёрские URL только у 6 букмекерских офферов; у остальных **87 офферов поле ссылки пустое**. Они включены и видны в каталоге, но создание сделки блокируется, пока администратор не добавит проверенную персональную ссылку в админке. Ссылки не генерируются и не угадываются автоматически. Для БК дополнительно требуется записать письменное согласование cashback-формата.

Для каждого оффера сгенерировано индивидуальное тематическое изображение в `assets/offers/<категория>/<код>.jpg`: название, сумма награды и краткое условие. Это авторские иллюстрации, а не официальные фотографии карт или логотипы рекламодателей.

### Возрастные ограничения

- Марафон Бет — 21+ (как указано владельцем для размещений).
- Микрорезерв — 21–75.
- Kviku и Возьмика — 18–65.
- Давака — 18–75.
- Остальные, включая Балтбет, Мелбет, МТС Деньги и Альфа-Банк — 18+ по умолчанию.

Для ограниченных диапазонов бот спрашивает число полных лет непосредственно перед созданием заявки; дату рождения не собирает. Это самодекларация пользователя, а не проверка документа.

## Как устроена сделка

1. Пользователь выбирает категорию и оффер. Карточка показывает сумму, целевое действие, возраст, срок холда, шаги проверки и список нужных доказательств.
2. После «Взять в работу» создаётся сделка с персональным `subid`. В снимок сделки копируются наименование, условие, награда, холд, возраст, ссылка и список доказательств — последующие правки оффера не меняют старую сделку.
3. Пользователь отправляет доказательства. Допускаются фото и документы; новые файлы можно досылать, пока сделка рассматривается или находится в холде.
4. Администратор проверяет доказательства и может: отклонить с причиной, перевести в ручной холд либо вручную начислить вознаграждение.
5. Партнёрский postback `pending/hold` переводит заявку в ожидание сети. Postback `approved/confirmed` запускает настроенный срок холда. После его истечения планировщик только уведомляет администратора и помечает сделку для финальной проверки; награда автоматически не начисляется. Администратор проверяет доказательства и вручную подтверждает сделку.
6. Postback `rejected/declined` отклоняет сделку; если награда уже начислялась, выполняется обратная финансовая проводка (clawback), в том числе по реферальному начислению.

**Статусы сделки и денег не смешиваются:**

- Оформляется — пользователь получил ссылку, но ещё не отправил доказательства.
- На рассмотрении — доказательства поступили и ждут проверки.
- В холде — лид принят/передан на проверку сети; доступ к деньгам ещё закрыт.
- Доступно — сделка подтверждена, награда внесена в кошелёк.
- Отклонено / истекло — начисления нет.

`payouts` — отдельный процесс вывода: ожидание → обработка → выплачено либо отклонено с возвратом денег. Если партнёр отзывает уже начисленный лид, не взятые в работу запросы автоматически отменяются с возвратом резерва; запросы в обработке блокируются в статусе `review_required` и требуют сверки фактического банковского перевода. Отмена пользователем разрешена только пока администратор не взял запрос в работу.

## Карты: что проверять

Сценарий индивидуальный для каждой карты, ровно по ЦД из каталога. Для карты без расходной операции нужен скрин выпуска/выдачи/активации. При наличии требования покупки нужны оба подтверждения: статус карты и операция с видимыми датой и суммой. Условия конкретного оффера можно редактировать в админке.

Для сверки владельца на первом скрине личного кабинета ФИО должно быть видно полностью. На остальных скринах ФИО можно скрыть, если его достаточно на первом. Во всех доказательствах необходимо закрывать паспортные данные, дату рождения, телефон, адрес, полный номер карты/счёта, баланс, чужие операции и любые коды. Никогда не запрашивай CVV/CVC, PIN, SMS/OTP-коды, пароли, скан паспорта или полный экран с персональными данными.

## БК: два разных обязательства

Для рассмотрения сделки нужны три отдельных подтверждения: профиль букмекера с ФИО и отметкой идентификации; история пополнений с датами и суммами; рассчитанная квалифицирующая ставка с событием, датой, суммой, коэффициентом и итоговым статусом. Если приветственный фрибет является отдельным условием конкретной промоакции, приложи ещё и экран его начисления/активации. Пароль, OTP, полные платёжные реквизиты и сканы документов не отправляются.

Партнёрское ЦД (регистрация/депозит/ставка) и приветственный бонус самой БК — разные вещи. Сумма «Я плачу» в каталоге — награда пользователю за подтверждённый лид. Фрибет/бонус БК — отдельная промо-акция со своими правилами и не является гарантированным доходом.

В карточке каждого букмекера показывается актуальная проверяемая информация/оговорка из `notes`, а в админке редактируются источник правил и условия. Для всех 6 БК требуется письменное согласование cashback-формата и типа трафика; без `network_status=approved` кнопка оформления блокирует создание сделки. ## МФО и CPL

**МФО:** целевое действие в каталоге — фактическая выдача займа. Комплект состоит из двух отдельных доказательств: (1) личный кабинет с полностью видимым ФИО и статусом «Одобрено»; (2) подтверждение «Займ выдан/Деньги перечислены» с датой и суммой. Одобрение без фактической выдачи не подтверждает ЦД «выдача займа». В обоих скринах нужно закрыть паспортные данные, дату рождения, телефон, адрес, номер договора, платёжные реквизиты и лишние сведения. Вознаграждение начисляется только после подтверждения сети, но не должно побуждать пользователя брать заём исключительно ради кэшбэка. Перед оформлением пользователь должен прочитать ПСК, ставку, срок, полную сумму возврата и условия просрочки у кредитора. Администратор может заполнить ПСК/ставку/срок/реестр в карточке; если сведения неизвестны, их нельзя выдумывать.

**CPL:** целевое действие — принятая/валидная заявка или привязка карты в соответствии с конкретным оффером. Достаточно одного скриншота из кабинета сервиса с нужным статусом и датой; займ оформлять не нужно, если это прямо не указано в ЦД. Займ брать не требуется, если это прямо не указано в ЦД. Пользователю сообщается о передаче анкеты партнёрам и возможных звонках/SMS.

## Пользовательский интерфейс

- Русское меню и тексты.
- Каталог по четырём категориям, отдельное изображение каждого оффера.
- Мои сделки, история статусов, доказательства и поддержка по каждой сделке.
- Кошелёк показывает: оформляются, на рассмотрении, в холде, доступно, зарезервировано под вывод и выплачено.
- Реквизиты СБП в настройках: банк и телефон; телефон шифруется Fernet. При запросе вывода реквизиты копируются в заявку и не меняются задним числом.
- Реферальные начисления учитываются отдельно и имеют уникальные ключи финансовых операций.

## Админка Telegram: `/admin`

- **Скрины / очередь проверки:** новые полные комплекты по сделкам на рассмотрении и в холде; открыть сделку и все файлы; видеть обязательный чек-лист; начислить сейчас (только если все пункты загружены и пользователь явно отправил комплект); перевести в холд; запросить дополнительные сведения; отказать с причиной. Повторно отправленный комплект по сделке в холде возвращается в очередь один раз; просмотренный комплект не дублируется. Поддерживаются фото, изображения-документы и PDF. Запрошенные дополнительные доказательства должны быть загружены после запроса.
- **Холды:** посмотреть ожидающие и истёкшие сделки. По окончании срока планировщик создаёт одно уведомление и событие истории; он не начисляет деньги. Администратор проверяет доказательства и решение сети, затем вручную подтверждает начисление либо запрашивает данные/отказывает.
- **Запросы на вывод:** отдельные заявки pending/processing/review_required с суммой, зафиксированным банком и номером СБП. Администратор сначала берёт запрос в работу, затем отмечает фактический перевод либо отклоняет с причиной и возвращает деньги на баланс.
- **История выплат:** хронология создания, взятия в работу, оплаты, отклонения/отмены, комментарии и кто совершил действие.
- **История сделок:** снимок условий и ссылок, выплата сети, пользовательская награда, доказательства и русскоязычный аудит событий.
- **Офферы:** включение/отключение, редактирование ЦД/наград/выплаты сети/холда/возраста/minimum/tracking-параметра/ссылки/источника правил/шагов и списка доказательств. История хранит администратора, дату и описание изменений; секретные параметры партнёрских ссылок в текст аудита не копируются. Для БК любое существенное изменение ссылки или условий сбрасывает письменное согласование до повторного подтверждения.
- **Статистика:** пользователи, сделки по статусам, сумма postback, подтверждённый пользовательский кэшбэк, реферальные начисления и выплаченные запросы. Доход сети неизвестен, пока его не прислала сеть.
- **CSV выплат:** выгрузка реестра; в файле есть платёжные реквизиты, поэтому хранить его нужно ограниченно.
- **Поддержка:** пользователь может написать по отдельной сделке; администратор отвечает командой `/reply <telegram_id> <текст>`.

Редактор оффера принимает 10 полей через `|`:

`Название | условие | выплата сети ₽ (0 неизвестно) | награда пользователю ₽ | холд дней | минимум покупки/депозита ₽ | возраст 18-75 | параметр subid | партнёрская ссылка | официальный источник правил`

## Финансовые статусы

Баланс — доступные пользователю деньги. Запрос вывода резервирует сумму из баланса и не позволяет потратить её повторно. При отмене/отклонении резерв возвращается ровно один раз через уникальную запись `wallet_entries`. Перевод считается выполненным только после ручного подтверждения администратором, автоматические выплаты API пока не подключены.

Начисления и сторно сохраняются в `wallet_entries` с уникальным `ref`. Если сеть отзывает уже выплаченный лид, обратная проводка может привести к отрицательному балансу пользователя — это фиксирует задолженность/корректировку, не скрывая ранее совершённый вывод.

## Технологии и безопасность

- PostgreSQL 16 — основная БД в Docker Compose.
- Alembic — миграции схемы (`alembic upgrade head`).
- Redis — FSM aiogram.
- Fernet — шифрование телефона СБП; хеш — поиск совпадений. Ключ `PHONE_ENCRYPTION_KEY` хранить отдельно и резервировать; потеря ключа означает невозможность расшифровать старые номера.
- Антифрод доказательств: перцептивный pHash сохраняется в отдельном реестре `proof_fingerprints` по каждому офферу. Точный повтор на том же оффере блокируется, включая загрузку с другого Telegram-аккаунта; похожие изображения помечаются для ручной проверки. Уникальное ограничение БД закрывает гонку параллельных загрузок. Исторические pHash переносятся миграцией. PDF/HEIC в текущем алгоритме не получают визуальный pHash и требуют ручной проверки.
- Postback — `POSTBACK_SECRET`; в `postbacks.raw` записываются только whitelisted-поля `subid/status/payout`, произвольные query-параметры не сохраняются.
- Для повторных операций используются уникальные идентификаторы проводок. Для старых сделок с одним универсальным скрином новый многошаговый чек-лист нельзя обойти: если требуется несколько подтверждений, их нужно дослать и отправить комплект повторно.

## Запуск

### 1. Подготовь секреты

В Windows PowerShell можно выполнить `powershell -ExecutionPolicy Bypass -File .\scripts\create_env.ps1`: скрипт запросит токен и Telegram ID, сгенерирует независимые секреты и создаст `.env`. Альтернатива — скопировать `.env.example` в `.env`, заполнить токен и ID и сгенерировать секреты вручную.

Для ручной генерации каждого hex-секрета используй:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Запусти команду отдельно для `HASH_SALT`, `PHONE_ENCRYPTION_KEY`, `POSTBACK_SECRET` и `POSTGRES_PASSWORD`. Не используй один секрет в нескольких полях и не коммить `.env`. Пароль PostgreSQL состоит из hex-символов, поэтому его удобно вставлять в URL без дополнительного кодирования.

### 2. Запусти сервисы

```bash
docker compose up -d --build
docker compose logs -f bot
```

Контейнер бота выполняет `alembic upgrade head`, затем синхронизирует каталог и запускает Telegram polling + HTTP endpoint. Health endpoint: `http://localhost:8080/health`. Команда `/admin` доступна только ID из `ADMINS`.

### 3. Настрой партнёрские сети

В админке добавь подтверждённые URL, проверь `subid`-параметр и формат postback. Для каждого BK зафиксируй письменное разрешение на cashback-трафик и только затем используй действие «Согласовано». Нельзя включать невалидную ссылку и считать, что postback работает, пока не получен тестовый callback от реальной сети.

### Формат postback

```text
GET /postback?secret=<POSTBACK_SECRET>&subid=<subid>&status=hold&payout=0
GET /postback?secret=<POSTBACK_SECRET>&subid=<subid>&status=approved&payout=1800
GET /postback?secret=<POSTBACK_SECRET>&subid=<subid>&status=rejected&payout=0
```

Допустимые статусы сети: `pending/hold`, `approved/confirmed/accepted/1`, `rejected/declined/cancelled/2`. Названия и формат параметров адаптируй под документацию каждой сети. `payout` — комиссия сети, а не награда пользователю.

## CI

GitHub Actions (`.github/workflows/ci.yml`) запускается на каждый push и pull request в любую ветку: `backend` — pytest на Python 3.11, `frontend` — `npm ci`, `tsc --noEmit`, тесты и сборка Vite на Node 22. Job `docker` собирает образ `bonvera:ci` только на push в `main` и `feat/**`, без пуша в registry; секреты не используются.

Автотесты проверяют состав каталога, диапазоны возраста, уникальность кодов, наличие 93 изображений, шаблоны доказательств для каждого типа оффера, пошаговую отправку, повторную очередь проверки и финансовые правила отзыва лида. В текущей проверке: **21 тест пройден**; Python-компиляция `bot` и Alembic также пройдена. Интеграционный тест реального Telegram API, PostgreSQL/Redis, реальные postback-и и фактический перевод денег должны быть выполнены в окружении владельца с его токенами/учётными данными. Текущая сборка не подключена к действующему Telegram-боту и не может самостоятельно выполнить банковский перевод.
